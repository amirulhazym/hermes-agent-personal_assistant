# Session Cycling / Phantom Message Flood — Production Incident (2026-07-16)

## Environment
- VPS: Tencent Lighthouse (Singapore), 1.9GB RAM, 2-core
- Bridge: @whiskeysockets/baileys (bridge.js, 765 lines)
- Bridge PID: 1178352 (10h uptime at time of incident)
- Gateway: Hermes (Python), last restarted 00:38 MYT
- WhatsApp SIM: Maxis (Malaysia) — display name "MJ Hermes Maxis"

## Evidence Chain

### Bridge log explosion
```
# Before (stable): 17,355 lines
# 2 minutes later (cycling): 43,663 lines
# Delta: +26,308 lines in ~2 minutes = ~219 lines/second
```

### "Closing session" pattern (repeated ~200+ times)
Every entry follows the same structure:
```
Closing session: SessionEntry {
  _chains: { ... chainKey, messageKeys {} },
  registrationId: 1676418050,
  ...
  indexInfo: {
    closed: -1,  ← current session being opened
    ...
  }
}
Removing old closed session: SessionEntry {
  ...
  indexInfo: {
    closed: 1784169154198,  ← previous session with close timestamp
    ...
  }
}
```

The `closed: -1` for new sessions followed immediately by removal of `closed: <epoch_ms>` old sessions is the hallmark of Baileys rapidly tearing down and recreating crypto sessions.

### Gateway phantom sends
Normal agent response has BOTH log entries:
```
response ready: ... chat=xxxx ... api_calls=N response=X chars
Sending response (X chars) to xxxx
```

Session cycling sends have ONLY:
```
Sending response (23 chars) to xxxx
```
No "response ready" → not generated by the agent → generated by bridge layer replaying stale messages.

## Why It Floods All Groups
Baileys manages a single WebSocket connection to WhatsApp for all groups. When session cycling triggers message replay, the replays are broadcast to ALL groups the account participates in. This is why both "Account" and "Health & Med" received the flood simultaneously.

## WhatsApp Rate-Overlimit as Circuit Breaker
```
"Send failed: {\"error\":\"rate-overlimit\"}"
```
This is WhatsApp's SERVER-side rate limit (not API provider). It activates when too many messages are sent too quickly to the same chat. It prevents the feedback loop from running indefinitely.

## Recovery Method Used
Gateway restart via `systemctl --user restart hermes-gateway` was proposed but not yet executed at time of this writing. The bridge was still cycling but rate-limited by WhatsApp server.
