# WhatsApp Bridge Maintenance

## When to Use

- User asks why WhatsApp bridge memory is high or getting health monitor memory alerts
- User wants to understand restart types (gateway vs bridge vs reconnect)
- User asks about session file cleanup — what to delete, what's safe
- User asks about Node.js memory flags and whether they work
- User asks about upgrading Baileys or alternative WhatsApp solutions
- Bridge crashes repeatedly or disconnects frequently
- Evaluating free/self-hosted WhatsApp API alternatives
- User reports empty/blank dark message bubbles flooding WhatsApp groups from bridge
- Bridge log grows rapidly (thousands of lines in minutes) with "Closing session" / "Removing old closed session" entries

## Architecture Overview

```
User <-> WhatsApp <-> bridge.js (Node.js/Baileys) <-> HTTP port 3000 <-> WhatsAppAdapter (Python gateway)
```

- bridge.js: Node.js process running @whiskeysockets/baileys — manages WhatsApp Web connection
- WhatsAppAdapter (gateway/platforms/whatsapp.py): Python subprocess manager — spawns, polls, kills bridge
- Communication: REST-like HTTP on 127.0.0.1:3000 (not MCP, not WebSocket)
- Gateway spawns bridge via `subprocess.Popen(["node", "bridge.js", "--port", "3000", ...])`

## Diagnosis Procedure

### Step 1: Check current bridge state

```bash
# Bridge process memory + args
ps aux | grep bridge.js | grep -v grep
cat /proc/<PID>/cmdline | tr '\0' '\n'

# Bridge health endpoint
curl -s http://127.0.0.1:3000/health | python3 -m json.tool

# Overall system memory
free -h
swapon --show

# Top memory consumers
ps aux --sort=-%mem | head -15
```

### Step 2: Inspect session folder

```bash
# File count, total size
ls ~/.hermes/whatsapp/session/ | wc -l
du -sh ~/.hermes/whatsapp/session/

# Largest files (potential memory contributors)
ls -laSh ~/.hermes/whatsapp/session/ | head -20

# File type breakdown
ls ~/.hermes/whatsapp/session/ | awk -F. '{print $NF}' | sort | uniq -c | sort -rn
```

### Step 3: Check Node.js flags

```bash
# Check if --max-old-space-size is set
cat /proc/<bridge-PID>/cmdline | tr '\0' '\n'
```

If no `--max-old-space-size` flag is present, the bridge uses V8 default (~1.8GB on 2GB VPS).

### Step 4: Check Baileys version

```bash
cd /home/ubuntu/.hermes/hermes-agent/scripts/whatsapp-bridge
cat package.json | grep baileys
```

### Step 5: Check gateway adapter version

```bash
grep -A1 "class WhatsAppAdapter" ~/.hermes/hermes-agent/gateway/platforms/whatsapp.py
```

### Step 6: Diagnose Session Cycling / Phantom Message Flood

Use when user reports empty/blank dark bubbles flooding groups, or bridge log growing explosively.

Symptom pattern: WhatsApp groups receive dozens of empty/dark message bubbles from the bridge in rapid succession with no content. Affects ALL groups on the same connection simultaneously.

#### Evidence chain

```bash
# 1. Check bridge log growth rate — if it grew thousands of lines in minutes, session cycling is active
wc -l ~/.hermes/whatsapp/bridge.log
# Compare to 2 minutes later — should NOT grow by >100 lines passively

# 2. Check gateway log for "Sending response" without "response ready" — these are bridge-originated messages, not agent responses
grep "Sending response" ~/.hermes/logs/agent.log | tail -20
# If a message to a group chat has NO matching "response ready" entry, it's auto-generated by the bridge layer

# 3. Check for WhatsApp rate-limit blocks — the native anti-flood circuit breaker
grep "rate-overlimit\|Send failed" ~/.hermes/logs/agent.log

# 4. Check bridge log for session cycling pattern (rapid close/open)
grep -c "Closing session\|Removing old closed session" ~/.hermes/whatsapp/bridge.log
# Count > 100 in a short period = active cycling
```

#### Root cause

Baileys WebSocket connection becomes unstable (network jitter on VPS route, WhatsApp server session expiry, or accumulated internal state corruption). The library repeatedly closes crypto sessions and opens new ones. During this cycling, WhatsApp server re-delivers stale message receipts / presence notifications that appear as **empty/blank bubbles** — no text body, just delivery metadata.

#### Upstream effects

- Gateway may auto-respond to phantom messages (shows as "Sending response (N chars)" with no "response ready" in agent log)
- These auto-responses compound the flood until WhatsApp native rate-limit kicks in
- ALL groups on the connection receive the artifacts simultaneously
- Bridge log explodes (e.g. 17K → 43K lines in 2 minutes is a confirmed severity marker)

#### Immediate fix: use a controlled gateway restart only from an external supervisor/operator context. Do not run `systemctl --user restart hermes-gateway` or an equivalent self-termination script from the active gateway conversation; it can trigger the self-restart/auto-resume loop described above.

#### Recovery verification

```bash
# Bridge reconnected
curl -s http://127.0.0.1:3000/health | python3 -c "import sys,json; d=json.load(sys.stdin); print(d.get('status','unknown'))"
# Should print "connected"

# No more phantom sends to groups
grep "Sending response.*@g.us" ~/.hermes/logs/agent.log | tail -5
# After restart, should only show legitimate agent responses
```

## Reconnect-storm diagnosis: repeated 405/503 closes

A repeated `405` is not automatically proof of logout. In Baileys, 405 can be the status extracted from a WebSocket `Unexpected server response: 405`; the named disconnect enum may not contain 405. Treat the upstream trigger as **unresolved** until the raw disconnect payload, server location/reason, active Baileys/WA version, and session state are captured.

### Evidence pattern

1. Capture the first upstream `503`/stream error and the first `405` with timestamps.
2. Find the last successful `open` event and prove whether any later `open` occurred.
3. Count close events by time bucket. Dozens of closes per minute indicate overlapping reconnects, not a healthy retry loop.
4. Read the bridge source: if each socket's `close` handler calls `startSocket()` without a single-flight guard, socket-generation ownership, or backoff, the bridge can amplify one upstream failure into a reconnect storm.
5. Check `/health` and the actual delivery endpoint separately. An HTTP bridge process being alive does not mean WhatsApp transport is connected; generated cron output does not mean delivery succeeded.

### Recovery and permanent fix

- Immediate recovery: use the controlled gateway restart procedure to terminate the storm and create one clean bridge process; do not delete `creds.json` as a first response to 405.
- If 405 persists after a clean restart, investigate linked-device/session state and perform a backed-up re-pair only with explicit approval.
- Permanent bridge fix: single-flight reconnect, close/invalidate the previous socket before opening another, ignore stale socket events using a generation token, exponential backoff with jitter, bounded retries/manual state for 401/403/405/440, and structured logging of error payload + version.
- Implement this as a separately testable reconnect controller where possible. The regression test must prove: duplicate close events create one pending retry, startup failure schedules the next backoff retry, successful connection resets backoff, and stale generations cannot become active.
- Follow the candidate/live boundary strictly: syntax + isolated tests prove only the candidate; compare the candidate self-hash with `/health`'s runtime `scriptHash` after reload before calling the fix live. A changed source file, green unit tests, or successful process restart alone is not proof of recovered delivery.
- Verify with fresh `/health`, a real outbound message, and a quiet log window. Keep the live process on the old code until the candidate has passed its isolated tests and the reload is explicitly executed and verified.
- Detailed reproduction/evidence pattern: `references/reconnect-storm-controller-and-runtime-boundary-2026-07-29.md`.

### Gateway self-restart loop hard stop

Never execute a command from the active gateway agent that terminates or restarts that same gateway process. A child shell launched by the agent is still part of the gateway's active turn; killing the parent interrupts the tool call. Hermes may then auto-resume the interrupted session and replay the unfinished self-termination command, creating a restart loop.

Required safeguards:

1. Treat any restart script that targets the current gateway PID as a destructive external action, not a normal terminal step.
2. Do not stage or execute it from the active gateway conversation.
3. If a restart is necessary, use a separately triggered supervisor/systemd action with a one-shot/idempotent latch, or require an external operator action.
4. After an interrupted restart, inspect `systemctl --user show hermes-gateway.service`, the current PID, `NRestarts`, and restart-state before doing anything else.
5. If the gateway is already active and the bridge is connected, do not restart again; run live delivery verification instead.
6. Never mark the restart transaction verified when `new_pid`, `completed_at`, or outcome evidence is missing.

Detailed incident pattern and evidence: `references/self-restart-auto-resume-loop.md`.

### Recovery decision gate (mandatory)

Do not restart or re-pair automatically just because a health alert was emitted. First establish the current state:

1. If `/health` is disconnected and recent delivery attempts fail, preserve/verify the backup, then use the controlled gateway restart path.
2. If the bridge has already recovered, do **not** trigger an unnecessary restart. Run a real outbound delivery test and wait for a quiet log window.
3. Treat one successful health response or one successful send as **partial recovery**, not stable recovery. Require repeated health probes, a successful send, and—when possible—a destination-side reply/receipt.
4. Re-pair only after a backed-up session, a controlled restart, and fresh evidence that the existing session remains unusable. Never delete credentials as the first response to 405.
5. Keep the evidence boundary explicit: the WhatsApp UI timestamp may precede Hermes receive time; absent raw inbound logs/DB rows, label exact command receipt as unverified rather than inferring it from a later outbound response.

**Reference:** `references/bridge-405-reconnect-storm-2026-07-29.md` contains the evidence pattern and the specific monitor/transport boundary lesson.

## Session File Reference

All files in `~/.hermes/whatsapp/session/` (actual analysis from production system):

| File pattern | Purpose | Safe to delete? | Impact |
|---|---|---|---|
| `creds.json` | Auth credentials — the master key | **NO** | Must re-pair (QR scan) |
| `sender-key-*.json` | Group encryption keys | ⚠️ Regenerates from server | Slow reconnect per group |
| `session-*.json` | Device session states | ⚠️ Regenerates | Slow reconnect |
| `app-state-sync-*.json` | WhatsApp app state (critical block, regular_high, regular_low) | ⚠️ Regenerates | Very slow reconnect — full resync |
| `identity-key-*.json` | Cryptographic identity keys | **NO** | Others see "security code changed" |
| `pre-key-*.json` | Forward secrecy pre-key bundles | ✅ Yes | Replaced automatically |
| `lid-mapping-*.json` | LID-to-JID mappings | ✅ Yes | Regenerated |
| `device-list-*.json` | Paired device list | ✅ Yes | Regenerated |

**Key insight from production:** 2,134 files = only 9.4MB on disk. The memory problem is NOT disk space — it's V8 heap representation. Parsing these into JavaScript objects can multiply memory usage 50-100x.

## Restart Types (from code analysis — NOT theory)

| Type | Mechanism | Effect | Code location |
|---|---|---|---|
| **Gateway restart** | `systemctl --user restart hermes-gateway` | Python adapter sets `_shutting_down=True`, terminates bridge (SIGTERM→SIGKILL), releases lock, systemd re-spawns | `whatsapp.py:649-698` (disconnect) |
| **Bridge restart** | Kill bridge.js PID manually | Gateway detects via `_check_managed_bridge_exit()` → sets fatal error "whatsapp_bridge_exited" (retryable) → watcher restarts gateway | `whatsapp.py:617-647` |
| **WhatsApp auto-reconnect** | Baileys internal WebSocket reconnection on code 515 / signal loss | No process restart. Memory continues accumulating. Fastest recovery. | Built into Baileys library |
| **System reboot** | Full VPS reboot | Everything cold start. WhatsApp session credentials survive on disk. | N/A |

**Critical fact:** bridge.js has NO process signal handlers (verified: no `process.on('SIGTERM')` or `process.on('SIGINT')` anywhere in the 765-line script). It dies uncleanly on SIGTERM. This is fine because WhatsApp session data persists on disk in `creds.json`.

## Optimization Options (ranked by feasibility + impact)

### Option 1: Add --max-old-space-size (current stack, zero cost)

```bash
# Edit the spawn command in whatsapp.py to include memory limit
# Find: Popen(["node", str(bridge_path), "--port", ...)
# Change to: Popen(["node", "--max-old-space-size=768", str(bridge_path), "--port", ...])
```

- **Effect:** Sets V8 hard heap cap. When hit, GC runs more aggressively. If still exceed → process OOM-crashes.
- **Truth:** It works as a belt, not a cure. Prevents runaway memory from filling all RAM+swap, but doesn't fix the leak. If Baileys genuinely needs >768MB, it crashes.
- **Recommendation:** 512-768MB is reasonable. Test 24h. If bridge crashes, raise to 1024.

### Option 2: Auto-restart bridge via cron (current stack, zero cost)

```bash
# Cron every 4-6 hours kills the bridge — gateway auto-restarts it
*/5 * * * * kill $(cat ~/.hermes/whatsapp/session/bridge.pid 2>/dev/null) 2>/dev/null
```

- **Effect:** Fresh heap every N hours. Memory never accumulates beyond the interval.
- **Pitfall:** Gateway treats this as a crash — dispatches "WhatsApp bridge exited" fatal error notification each time. Need to distinguish intentional restarts.

### Option 3: Upgrade Baileys (low cost, medium effort)

- Check latest release at https://github.com/WhiskeySockets/Baileys/releases
- Current: v7.0.0-rc.9 (Release Candidate — not final stable)
- Update version in `package.json`, run `npm install`
- Memory fixes are incremental — each release has some optimizations but also new features

### Option 4: Alternative engines (proper fix, migration effort)

## Code Reference (WhatsAppAdapter lifecycle)

- **`connect()`** (line 332-597): Verifies Node.js exists, checks creds.json, acquires lock, auto-installs npm deps, spawns bridge, waits for health check, starts poll loop
- **`disconnect()`** (line 649-698): Sets _shutting_down=true, terminates bridge (SIGTERM then SIGKILL if timeout), cancels poll task, closes HTTP session, releases lock
- **`_check_managed_bridge_exit()`** (line 617-647): Polls bridge returncode. If non-None and not during shutdown, sets fatal_error (retryable=true)
- **`_spawn_bridge()`** (for Raft platform, line 516-541): Alternative bridge spawning path used by Raft adapter

## Pitfalls

- ❌ **Session file count is misleading** — 2,134 files looks like the problem but is only 9.4MB on disk. The real issue is V8 heap representation 50-100x larger.
- ❌ **--max-old-space-size is NOT automatic memory reduction** — it's a hard cap. Set too low and the bridge OOM-crashes silently. Monitor carefully.
- ❌ **Bridge.js has no signal handlers** — it dies uncleanly on SIGTERM. No cleanup, no graceful shutdown. This is by design (session data persists on disk).
- ❌ **Killing bridge alone is different from gateway restart** — gateway detects the crash, sets fatal error, watcher restarts. Slower recovery than a controlled gateway restart.
- ❌ **Deleting creds.json** means re-pairing with QR scan. Don't delete unless user explicitly wants to re-pair.
- ⚠️ **Gateway restart = ~30s of WhatsApp messages lost** — messages sent during the restart window won't be delivered.
- ⚠️ **Auto-restart cron triggers false crash alerts** — the health monitor sees bridge exit and sends "WhatsApp bridge died" notifications.
- ⚠️ **Node.js --expose-gc + manual gc()** can help but may cause jank (pause-the-world GC every call).
- ❌ **Session cycling is NOT memory-related** — it's a WebSocket stability / state corruption issue. Adding --max-old-space-size won't fix phantom message floods.
- ❌ **Do NOT kill bridge PID alone during session cycling** — gateway detects crash → sets fatal error → triggers "WhatsApp bridge died" notification. Always use `systemctl --user restart hermes-gateway` for clean recovery.
- ❌ **Session cycling affects ALL groups simultaneously** — messages landing in one group but not another does NOT rule out cycling; some groups may suppress empty artifacts differently.
- ⚠️ **Gateway auto-response to phantom messages compounds the flood** — if you see "Sending response" with no "response ready" in agent.log, the bridge is generating messages that the agent then tries to answer, creating a feedback loop. WhatsApp rate-limit (rate-overlimit) is the circuit breaker.

## Verification Steps

After any change:
1. `curl -s http://127.0.0.1:3000/health` — must return status "connected"
2. `free -h` — check available memory increased
3. Monitor for 30min — check memory trend (growing? stable?)
4. Send a test message — verify bridge still processes messages
5. Check bridge log for errors: `tail -50 ~/.hermes/logs/bridge.log`
6. If recovering from session cycling: verify gateway log shows no phantom sends (`grep "Sending response.*@g.us" ~/.hermes/logs/agent.log | tail -5`)
