# Live-vs-canonical chat/repository audit

Reusable reference for audits where chat history spans Telegram/WhatsApp and the owner asks whether live VPS work is committed and synced with an application repository's `main`.

## Failure pattern captured

A narrow check of `/home/ubuntu/hermes-agent-personal_assistant-work` can show `main == origin/main` while the actual live system still has uncommitted work in a nested source checkout, plugin repository, or mutable runtime root. The statement “nothing to commit/push” is therefore invalid unless every relevant lane has been inspected.

The 2026-08-25 case had all of these at once:

- canonical application clone: exact tip match, but an untracked `SOUL.md`;
- nested Hermes source: 16 tracked modifications, including three same-day code/test files, plus a divergent/unrelated history against the personal remote;
- Antigravity provider repo: 8 tracked + 2 untracked same-day paths, with HEAD matching its remote but a dirty working tree;
- `.hermes` runtime: a large mixture of source-like files, config, memory, generated data, credentials, databases, logs, and private state;
- wiki: three local documentation commits with no remote, plus generated bytecode.

Historical cross-check anchors from that incident:

- quoted EOD claim and follow-up: `@session:default/20260825_192511_4543f92c`, messages 124878–124890;
- provider/core patch activity: `@session:default/20260825_155950_130ad3`, around message 124610 onward;
- WhatsApp runtime code/data patch activity: `@session:default/20260825_093724_61bac1d0`, messages 122653–122718; message 122695 explicitly separated a pending source-clone Git commit from the completed live edits.

These anchors are evidence of what was discussed/done in those sessions, not a substitute for a fresh filesystem/VCS audit.

## Two-lane verdict model

Always emit separate rows for:

| Lane | Minimum proof | Typical verdicts |
|---|---|---|
| Canonical clone → intended remote | `git status --porcelain=v2 --branch --untracked-files=all`; local full SHA; direct `git ls-remote --heads <remote> <branch>` | `EXACT-TIP + CLEAN-TRACKED`, `PUSHED-BUT-DIRTY`, `LOCAL-ONLY`, `BEHIND`, `UNVERIFIED` |
| Live source/runtime → intended remote | same checks for nested/plugin repos; runtime path inventory; source/runtime classification | `DIRTY`, `DIVERGED`, `UNRELATED`, `RUNTIME-ONLY`, `SOURCE-CANDIDATE`, `UNKNOWN` |

`EXACT-TIP + CLEAN-TRACKED` is not the same as “system synced.” It says only that one clone’s tracked `HEAD` matches one remote ref.

## Read-only evidence sequence

1. **Scope and timestamp**
   - record the owner’s exact target (“live VPS vs my GitHub `main`”);
   - record MYT timestamp and prohibit `fetch`, checkout, index/ref writes, commit, push, stash, merge, rebase, and runtime writes.

2. **Discover lanes**
   - canonical app clone;
   - nested/live source clone;
   - provider/plugin repos;
   - runtime root;
   - wiki/docs repos;
   - all registered worktrees and stashes.

3. **Inspect each repo without mutating refs**
   ```bash
   git -C "$repo" status --porcelain=v2 --branch --untracked-files=all
   git -C "$repo" diff --name-status
   git -C "$repo" diff --stat
   git -C "$repo" worktree list --porcelain
   git -C "$repo" stash list
   git -C "$repo" branch -vv
   git -C "$repo" remote -v
   ```

4. **Pin current remote heads directly**
   ```bash
   git ls-remote --heads <remote-url> <branch>
   ```
   Do not treat a stale `origin/<branch>` tracking ref as current remote evidence. Do not fetch during a read-only audit.

5. **Separate pushed-branch proof from PR proof**
   - A local branch matching `origin/<branch>` proves only that the branch tip is remote-reachable; it does not prove a pull request exists or was merged.
   - A URL shaped like `https://github.com/<owner>/<repo>/pull/new/<branch>` is a PR-creation form, not a PR object, review, CI result, or merge proof.
   - Verify the actual PR object through the provider API/CLI, filtered by exact head owner and branch. An empty result is `NO PR FOUND`, not `PR CREATED`.
   - Keep these states separate: `COMMITTED-LOCAL-ONLY` → `PUSHED-BRANCH` → `PR-OPEN` → `REVIEWED` → `MERGED`.
   - If a pushed feature depends on a separate plugin/provider repository, verify that repository's direct remote head independently; a canonical-app PR does not publish the dependency.

6. **Classify stale tracking refs without mutating them**
   ```bash
   git -C "$repo" remote prune --dry-run <remote>
   ```
   Use the dry run to enumerate local remote-tracking refs absent from the current remote. `git remote prune <remote>` mutates local refs; it does not delete remote branches or local branches, but it is still outside a read-only audit and should not be used as a prerequisite for opening a PR. Keep `refs/remotes/origin/*` separate from `refs/remotes/upstream/*`; pruning `origin` cannot clean an upstream mirror. Preserve the stale-ref list before any later cleanup because it is audit evidence.

7. **Prove graph relation before saying ahead/behind**
   ```bash
   git -C "$repo" merge-base HEAD <remote>/<branch>
   git -C "$repo" rev-list --count HEAD..<remote>/<branch>
   git -C "$repo" rev-list --count <remote>/<branch>..HEAD
   ```
   If merge-base is empty, classify as `UNRELATED/DIVERGENT`; do not force-push or use `--allow-unrelated-histories` as an automatic fix.

8. **Cross-check “no code changes” claims**
   - search the relevant session(s) by exact session ID and message ID;
   - preserve raw patch/write/test tool messages, not only an assistant recap;
   - compare current file mtimes and `git diff --stat` for same-day paths;
   - treat a clean canonical clone as insufficient evidence about nested/live lanes.

9. **Classify dirty paths before suggesting a commit**
   - `SOURCE-CANDIDATE`: code/docs/tests with an identified intended repository;
   - `RUNTIME/CONFIG`: active config, memory, job state, databases, sessions, logs;
   - `PRIVATE/CREDENTIAL`: auth/token/key/PII/medical data;
   - `GENERATED/CACHE`: bytecode, caches, build output;
   - `BACKUP/SNAPSHOT`: preservation material;
   - `UNKNOWN`: no reliable provenance yet.

10. **Report exact boundaries**
   - “no local-only commits” means no committed commits proven absent from the direct remote;
   - “uncommitted” means dirty index/worktree/untracked state;
   - “pushed-but-dirty” means the tip is remote-reachable but the working tree has changes;
   - “not push-ready” means source/provenance/privacy/lineage/approval gates remain open.

## Minimal evidence ledger

Use one row per lane:

```text
lane:
path:
purpose:

local_head:
direct_remote_head:
merge_base:
remote_only_count:
local_only_count:
tracked_modified:
staged:
untracked:
ignored_relevant:
stash/worktrees:
same_day_paths:
path_classification:
verdict:
raw_evidence:
next_gate:
```

Do not replace exact path sets with counts. Do not include secret values in the ledger; path names and categories are sufficient.

## Correct conclusion pattern

Lead with the narrow truth and the wider contradiction:

> “The canonical clone’s tracked `main` matches its remote. That does **not** prove the live VPS is synced. The nested source/plugin/runtime lanes are separately dirty/divergent/local-only, so the system-level verdict is `PARTIAL / NOT SYNCED` until selected changes are classified and ported.”

Then state the safe next step: selective diff/provenance review. Do not automatically stage, commit, push, clean, reset, or force-update `main`.
